# Ferry 任务规划

版本:草案 v0.5(2026-11-17)。配套文档:[产品设计方案](product-design.md)。

v0.5 相对 v0.4 的变化:

- 1.1、1.3 完成,Dokploy 实测结论见 [dokploy-findings.md](dokploy-findings.md)。
- 一期(M1、M2)不做异地备份:迁移前备份改为导出到服务器本机,已实测可行;P7(S3 兼容存储)和异地备份推迟到 M3。

v0.4 相对 v0.3 的变化:

- 暂不做扫码登录。2.2 改为“工作通知验证码 + 个人令牌”:网页用验证码确认身份,agent 用个人令牌调用 MCP。
  不再需要登录回调地址和可信域名,本机也能对接真实平台。
- 组织架构同步(2.1)不依赖登录,1.7 完成后即可开始,本机用开发身份测试。
- P6 已确认:agent 有独立账号体系,MCP 配置支持自定义请求头。P5 增加发送工作通知的权限。

v0.3 相对 v0.2 的变化:

- 身份改为对接钉钉或企业微信(每套部署选一个),不接入企业 SSO,不部署 oauth2-proxy。
  M2 的 2.1 到 2.3 按此重写,增加可选的 2.11(企业微信适配器),M2 从约 31 人日降到约 29 人日。
- 当前阶段只在本机开发和测试,不做生产环境部署。新增“本机开发阶段”一节,说明用什么替代企业资源、哪些任务暂不做。
- M0 补充完成:组织架构接口和“本部门可见”判定(同部门或上级部门),每个应用一个 Dokploy 项目。

v0.2 相对 v0.1 的变化:去掉审批和多项推迟的功能后,总工作量从约 84 人日降到约 65.5 人日;
测试服务器从 2 台减为 1 台;管理员停用应用提前到 M2;代码包上传已在骨架阶段完成。

## 说明

- 工作量单位是“人日”,按一名熟悉 TypeScript 的全栈工程师估算。这些是粗略估计,
  没有对着真实的 Dokploy 实例和钉钉、企业微信验证过,外部系统对接的部分误差最大。
- 每个阶段结束时都有一个可以演示的验收结果。前一阶段没有验收通过,不建议开始下一阶段。
- 标了“需企业配合”的事项依赖 IT 或其他部门提供资源,要尽早发起,否则会卡住进度。

## 本机开发阶段(当前)

当前只在本机(Mac + Docker Desktop)开发和测试,不考虑生产环境部署。这样不需要等企业提供资源,可以马上开始。

用本机替代企业资源:

| 原本需要 | 本机替代 |
|---|---|
| 测试服务器(P1) | 本机 Docker Desktop。Dokploy 官方安装脚本面向 Linux 服务器,如果在 Mac 上跑不通,需要一个 Linux 虚拟机 |
| 泛域名解析(P2) | `*.apps.localhost`,浏览器会自动解析到本机 |
| 内部证书(P3) | 直接用 HTTP |
| 内网能否访问外网(P4) | 本机可以访问外网,不需要依赖镜像源 |
| 钉钉或企业微信(P5) | 拿到 P5 之前:开发用请求头加内存里的组织架构,工作通知打印到日志。拿到之后本机就能对接真实平台(不需要回调地址) |
| 员工的 agent 客户端(P6) | Claude Code 连接本地的 `/mcp`,用请求头带个人令牌,和员工的 agent 用法一致 |
| 备份存储(P7) | 不需要。迁移前备份存到 Dokploy 所在的服务器本机 |

本阶段暂不做:1.2(依赖镜像源)、3.6(生产环境部署配置)、3.7(员工使用说明和宣讲材料),共约 6 人日。
有了 P5 之后,真实的钉钉或企业微信接口(通讯录、工作通知)在本机就能验证(2.1、2.2)。

本机测不到、要到企业环境再验证的:内网能否访问外网、员工实际使用的 agent 客户端。

Docker Desktop 目前分配约 8GB 内存。Dokploy、Ferry 的数据库、每个应用各自的数据库会同时运行,建议调到 12GB 以上。

1.3 的结论(2026-11-17,详见 [Dokploy 接口实测结论](dokploy-findings.md)):三个接口都能用,下面三种退路都不需要。

- 上传部署:`application.dropDeployment` 可以用 API key 调用。
- 一次性命令:没有专门接口,用“手动触发定时任务”(`schedule.create` + `schedule.runManually`)在应用容器里执行,同步返回成败。
- 按需备份:`backup.manualBackupPostgres` 可用,但只能备份到 S3 兼容存储。一期不用它,迁移前备份改为在服务器本机执行 pg_dump(已实测)。

实测中发现、1.4 和 1.5 要处理的细节:

- 应用和数据库建在项目的“环境”(environmentId)下。适配器接口里的 `createProject` 要同时返回环境 ID。
- Dokploy 会给名称加随机后缀,数据库的内部主机名要用接口返回的值。
- `application.saveEnvironment` 整体覆盖全部环境变量。适配器的 `setEnv`(约定是合并写入)要先读出原值,合并后再写回。
- 部署显示完成后,前几秒访问返回 502,健康检查要重试。
- 发布单里记录的备份 ID 应当是这次备份的 deploymentId 或文件路径,而不是 Dokploy 的备份配置 ID。
- `project.remove` 不会删除项目下正在运行的应用和数据库,下线时必须先逐个删除(任务 2.6)。

原先准备的三种退路(已不需要,留作参考):

- **上传部署不能用 API key 调用**:Ferry 接收代码包的部分不受影响,但需要改为由 Ferry 自己构建镜像再交给 Dokploy,或退回 Gitea 方案,工作量增加约 3 到 4 人日。
- **没有执行一次性命令的接口**:数据库迁移改为在应用启动时执行,模板要相应调整。
- **没有按需备份的接口**:迁移前备份改为 Ferry 直接连数据库导出。

1.8 的恢复逻辑是用假平台测试的,假平台的调用都是同步完成的。接真实 Dokploy 时,1.4 和 1.5 还要满足:

- **不和中断前的操作重叠。** Ferry 退出时,Dokploy 上的构建或迁移可能还在跑。恢复后重新部署或执行迁移之前,
  先查这个应用有没有进行中的部署或命令,有就等它结束。两个迁移同时作用于一个数据库会损坏数据,
  “迁移可以重复执行”并不能保证并发安全。
- **按名称查找已有资源。** 建好项目、应用或数据库后、记下 ID 前进程退出,恢复时会再建一个。
  创建前先按名称查找,找到就复用。
