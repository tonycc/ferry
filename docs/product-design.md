# Ferry 产品设计方案

版本:草案 v0.5(2026-11-17)

v0.5 相对 v0.4 的变化:一期不做异地备份。迁移前备份存到服务器本机,防止迁移写坏数据;
定时备份和异地备份(需要 S3 兼容存储)推迟到全公司推广前。

v0.4 相对 v0.3 的变化:暂不做扫码登录。身份确认改为通过钉钉或企业微信的工作通知发送验证码;
agent 用 Ferry 签发的个人令牌调用 MCP(员工的 agent 有独立账号体系,支持自定义请求头);
组织架构同步可以先于登录完成。

v0.3 相对 v0.2 的变化:不接入企业 SSO(OIDC、SAML),登录和组织架构改为对接钉钉或企业微信,每套部署选其中一个;
登录网关不再使用 oauth2-proxy,由 Ferry 自己完成登录和权限判定;明确“本部门可见”的规则(同部门或上级部门);
每个应用在 Dokploy 上单独一个项目。

v0.2 相对 v0.1 的变化:去掉审批,发布全部自动完成,改由管理员事后停用;去掉依赖漏洞扫描、闲置回收、
独立监控和访问内部系统的申请机制;管理后台缩减为应用列表和停用;代码提交方式改为上传代码包,不再部署 Gitea。

## 1. 背景与目标

企业里的普通员工已经可以用 agent 做出能用的小应用,但做完之后无法自己把它放到公司服务器上给同事使用:
部署需要懂服务器、数据库、域名和证书,而这些员工没有开发经验。

Ferry 要解决的问题是:**员工在 agent 里确认发布后,应用自动部署到企业内部服务器,并得到一个可以分享给同事的内网地址**,
体验接近把应用发布到公有云平台。

目标:

- 员工从确认发布到拿到访问地址,全程不需要接触任何技术概念,也不需要等待任何人批准。
- 发布失败时由 agent 自动修复,修不好时用员工能看懂的话说明原因。
- 平台对企业是可控的:谁发布了什么、谁能访问都有记录,管理员可以随时停用任何应用。

不在范围内:

- 不做 agent 本身,也不做应用的开发环境。Ferry 只负责“做完之后”的部分。
- 不面向专业研发团队的生产系统,不替代现有的 CI/CD。
- 不支持公网访问,只在企业内网使用。
- 不做发布前审批。

## 2. 用户与角色

| 角色 | 是谁 | 在 Ferry 里做什么 |
|---|---|---|
| 发布者 | 没有开发经验的普通员工 | 在 agent 里确认发布;在“我的应用”里查看、更新、下线自己的应用 |
| 访问者 | 发布者的同事 | 用钉钉或企业微信收到的验证码登录后,访问被授权的应用 |
| 平台管理员 | IT 运维 | 查看全部应用,随时停用或恢复任意应用,处理 agent 修不好的失败 |

发布者与 Ferry 的交互全部通过 agent 对话完成,“我的应用”网页是补充,不是必经之路。

## 3. 核心使用流程

### 3.1 首次发布

首次使用前,员工在 Ferry 网页上确认身份、领取个人令牌,填进 agent 的 MCP 配置。这一步只做一次(见第 5 节“身份与组织架构”)。

1. 员工在 agent 里说“发布这个应用”。
2. agent 展示发布摘要(应用名、访问地址、谁能访问),员工确认。
3. agent 调用 Ferry:创建应用、提交代码、发起发布。
4. Ferry 依次完成密钥扫描、建数据库、绑定域名、构建部署、数据库迁移、健康检查。
5. agent 告诉员工访问地址。

整个过程没有人工环节。目标耗时:从确认到拿到地址不超过 5 分钟。

### 3.2 更新应用

员工让 agent 修改应用后再次确认发布。Ferry 复用已有的数据库和域名,只部署新代码。
迁移前自动备份数据库。新版本不可用时自动恢复到上一个版本,员工的同事不会看到坏掉的应用。

### 3.3 发布失败

- 构建、迁移、健康检查失败:Ferry 把日志和修复提示交给 agent,agent 改完代码自动重新发布,最多 3 次。
- 3 次仍失败或遇到无法修复的问题:agent 用通俗的话告诉员工原因,并通知平台管理员。

### 3.4 访问应用

同事打开地址,未登录时跳转到 Ferry 的登录页,用钉钉或企业微信收到的验证码登录;登录一次后访问其他应用不用再登录。
Ferry 按应用的可见范围和组织架构决定放行还是拒绝(规则见第 5 节“身份与组织架构”)。
员工写的应用自身不需要实现登录功能。网关放行时会把访问者的身份(用户 ID、姓名、所属部门)放在请求头里传给应用,
需要区分“谁在用”的应用(如“我的请假记录”)直接读取即可(任务 2.3)。

### 3.5 管理员停用应用

管理员发现某个应用有问题(例如存放了不该存放的数据、占用过多资源)时,可以随时停用它:

- 服务立即停止,所有人(包括负责人)都无法访问。
- 负责人不能再发布这个应用;正在进行中的发布会被终止。
- 负责人收到通知和停用原因。
- 数据和配置保留。管理员可以恢复应用,恢复后和停用前一样可用。

因为没有发布前审批,停用是平台唯一的管控手段,所以它必须在开放给员工试用之前可用。

### 3.6 下线

员工可以随时下线自己的应用:访问地址立即失效,数据库停止但数据保留,应用名仍归自己;重新发布即恢复,原来的数据还在。
数据不会自动删除:平台管理员在管理页上手动删除已下线或已停用的应用(删除数据库连同数据、备份、代码包和记录,释放应用名,
通知负责人),删除后无法恢复。管理页显示每个应用下线了多少天,方便管理员判断。
回滚只恢复到上一个上线过的版本的代码,不恢复数据库。员工离职时(同步组织架构时能发现),由管理员停用其应用或转交给同事。

## 4. 功能设计

优先级:P0 是跑通真实部署所必需的,P1 是开放给员工试用所必需的,P2 是全公司推广所必需的。

### 4.1 发布

| 功能 | 说明 | 优先级 |
|---|---|---|
| 一键发布 | 一次确认完成全部部署步骤,没有人工环节 | P0 |
| 应用清单 | 代码根目录的 `app.yaml` 声明端口、数据库、迁移命令、可见范围 | P0 |
| 应用模板 | agent 从平台提供的模板起步,保证应用符合部署约定 | P0 |
| 自动建数据库 | 首次发布时创建,连接串直接注入应用,不经过 agent | P0 |
| 自动域名和证书 | 地址为 `应用名.apps.<企业域名>`,使用泛域名证书 | P0 |
| 发布进度和结果 | agent 可查询当前步骤和结果 | P0 |
| 失败自动修复 | 结构化错误回传给 agent,自动重试并限制次数 | P1 |
| 自动回滚 | 新版本健康检查失败时恢复上一个版本 | P1 |
| 手动回滚 | 员工要求恢复到上一个版本 | P1 |
| 迁移前备份 | 每次数据库迁移前自动备份,存在服务器本机 | P1 |

### 4.2 访问控制

| 功能 | 说明 | 优先级 |
|---|---|---|
| 统一登录 | 所有应用在网关层要求登录,用钉钉或企业微信工作通知收到的验证码确认身份,登录一次全部应用通用 | P1 |
| 个人令牌 | agent 用个人令牌调用 Ferry;员工可以作废后重新生成,离职时自动作废 | P1 |
| 组织架构同步 | 定时从钉钉或企业微信同步部门树、人员所属部门和在职状态 | P1 |
| 可见范围 | 仅自己、本部门、全公司三档,由员工自行选择,默认仅自己。“本部门”包含上级部门,见第 5 节 | P1 |

### 4.3 应用管理

| 功能 | 说明 | 优先级 |
|---|---|---|
| 我的应用列表 | 名称、地址、状态、可见范围 | P1 |
| 运行日志 | agent 和网页都能读取,用于排查问题 | P1 |
| 下线应用 | 删除服务,数据保留,重新发布即恢复;管理员可以手动彻底删除 | P1 |
| 发布历史 | 每次发布的时间、结果和版本 | P2 |

### 4.4 管理端

| 功能 | 说明 | 优先级 |
|---|---|---|
| 全部应用列表 | 负责人、负责人当前所在部门、可见范围、状态 | P1 |
| 停用和恢复应用 | 随时停用任意应用,可填写原因,可恢复 | P1 |

管理端只做这两项。服务器资源、容器状态、日志等运维信息直接使用 Dokploy 自带的界面。

### 4.5 安全与合规

| 功能 | 说明 | 优先级 |
|---|---|---|
| 凭据隔离 | 平台凭据只在 Ferry 内部,agent 和员工都拿不到 | P0 |
| 发布者身份 | 用钉钉或企业微信账号确认发布者是谁 | P1 |
| 密钥扫描 | 发布前检查代码里是否有硬编码的密钥 | P2 |
| 网络隔离 | 每个应用和它的数据库在自己的网络里:应用之间、应用和别的应用的数据库之间不能互访,应用也连不到 Dokploy;同事只能经登录网关访问应用(已实现,任务 3.2) | P2 |
| 审计日志 | 记录谁在何时发布、下线、停用、恢复了什么 | P2 |

### 4.6 资源与运维

| 功能 | 说明 | 优先级 |
|---|---|---|
| 配额 | 每人应用数上限,每个应用的 CPU 和内存上限 | P1 |
| 定时备份和异地备份 | 数据库每天备份,保留若干天,存到独立的 S3 兼容存储 | P2 |
| 告警 | 发布连续失败、备份失败时通知管理员 | P2 |
| 离线依赖源 | 内网无法访问外网时的 npm、pip、镜像代理 | 视网络环境,可能是 P0 |

### 4.7 明确推迟的功能

等有真实需求后再做:

- 发布前审批、访问内部系统的申请流程。
- 依赖漏洞扫描。
- 闲置应用自动休眠。
- 预览环境、按人或群组授权。
- 独立的监控系统和完整的管理后台。
- 应用数据进入 AI Hub(见第 5 节“与 AI Hub 的关系”)。
- 同一套部署同时接入钉钉和企业微信、同一个人在两个平台的账号合并。
- 接入企业 SSO(OIDC、SAML)。
- 钉钉、企业微信扫码登录(体验比验证码好,但要处理回调地址的可信域名限制)。

## 5. 系统架构

```
员工 → Agent 客户端 ──MCP──┐
员工 → “我的应用”网页 ─REST─┤
管理员 → 管理页面 ────REST─┤
                            ▼
                  Ferry 发布编排服务(Publisher)
        接入层 → 发布状态机 → 适配器          状态库
                     │           │       │
                  Dokploy     密钥扫描  钉钉 / 企业微信
                     │              (组织架构、工作通知)
        Traefik → 应用容器 → 数据库 → 备份存储
           │
           └ forwardAuth → Publisher /authz(登录 + 权限判定)
```

关键设计决定:

- **Ferry 是唯一能调用 Dokploy 的组件。** agent 只能调用 Ferry 提供的几个工具,拿不到任何平台凭据。
- **不修改 Dokploy 源码。** 全部通过 API 使用,升级不受影响,也避开其 `/proprietary` 目录的授权限制。
- **发布是持久化的状态机。** 每一步执行前先检查资源是否已创建,重试和重启都不会重复建资源。
- **发布不设审批,管控靠事后停用。** 状态机每一步开始前都会检查应用是否已被停用。
- **访问控制放在网关层。** Traefik 对整个应用域名统一调用 Ferry 的 `/authz`,由 Ferry 完成登录和权限判定,
  不再单独部署 oauth2-proxy 之类的登录服务。员工的应用不需要自己实现登录。
- **每个应用在 Dokploy 上单独一个项目。** 应用和它的数据库放在同一个项目里;不按部门分组,因为一个人可能属于多个部门,也会调岗。
- **数据库只自动备份,不自动恢复。** 回滚只恢复代码。恢复数据会丢失备份之后的写入,必须由人确认。

### 代码提交方式

采用**上传代码包**,不部署 Gitea,员工的电脑上也不需要 git。这一步由 agent 自动完成,员工不参与:

1. agent 调用 `prepare_app`,拿到一个一次性的上传地址和一个版本号。
2. agent 把应用目录打成 zip(排除 `node_modules`、`.git`、`.env` 等),用一次 HTTP PUT 传到上传地址。
3. agent 用版本号调用 `publish_app`。

上传地址里的令牌就是凭据:只对这一个应用的这一次上传有效,用过即作废,默认 15 分钟过期,
Ferry 只保存它的哈希。所以 agent 不需要持有任何长期凭据。Ferry 按版本保存代码包,回滚时用上一个版本的包重新部署。

Ferry 这一侧已经实现。**前提**是 agent 能在员工电脑上读取文件和执行命令;纯网页聊天的 agent 做不到,
需要换一种提交方式(见第 9 节问题 1)。

**已在本机实测确认**(任务 1.3):Ferry 可以用 API key 调用 `application.dropDeployment`,把代码包交给 Dokploy 构建部署,详见 [Dokploy 接口实测结论](dokploy-findings.md)。

代码结构和发布状态的细节见根目录 [README](../README.md)。

### 身份与组织架构

不接入企业 SSO,也不做注册和密码。员工账号和部门全部来自钉钉或企业微信。

**每套部署只对接一个平台**,在配置里指定。为了以后能同时接入多个平台,现在就遵守两条约定:

- 用户 ID 和部门 ID 都带平台前缀,如 `dingtalk:123`、`wecom:zhangsan`。两个平台的 ID 互相独立,可能重复。
- 业务代码只依赖组织架构接口(“用户属于哪些部门”“部门有哪些上级”),不直接调用平台 API。

以后要同时支持两个平台,只需加载两个适配器、在登录页让员工选择平台,数据和权限判定不用改。
接入时一个平台写一个模块,同时负责组织架构同步和发送工作通知;不预先做通用的身份平台框架。

**确认身份:工作通知验证码**

暂不做扫码登录。员工在 Ferry 的登录页输入自己的账号(手机号或工号,按组织架构查找),
Ferry 通过钉钉或企业微信的工作通知把一次性验证码发给这个人,员工填回验证码即完成身份确认。
只有本人能收到这条通知,所以这本身就证明了身份。

- 验证码 6 位,5 分钟内有效,只能用一次;同一账号连续输错多次后暂时锁定,发送也要限制频率。
- 不需要登录回调地址,不受可信域名限制,本机也能对接真实平台测试。
- 只有组织架构里在职的人才能登录。

**网页登录**

身份确认后,Ferry 签发自己的登录 cookie,**只发给 Ferry 自己的域名**,不覆盖 `*.apps`。
员工应用是任意代码,如果能收到 Ferry 的登录 cookie,就能拿它以访问者的身份调用 Ferry 的接口(比如下线他的应用)。
所以访问应用要用单独的、只对那一个应用有效的凭据(任务 2.3:未登录时跳到 Ferry 登录,再带着一次性凭据跳回应用,
由网关在应用域名下设置只有 `/authz` 认的 cookie)。

员工应用和 Ferry 同属一个站点时,浏览器仍会给应用发起的请求带上 Ferry 的 cookie,所以用 cookie 做修改操作时,
Ferry 要求请求来自它自己的页面(检查 `Origin`)。生产环境建议把应用放在和 Ferry 不同的注册域名下。

MCP 只认个人令牌,不认登录 cookie。

**agent:个人令牌**

员工用的 agent 有自己独立的账号体系,不支持钉钉或企业微信登录,但 MCP 配置支持自定义请求头。
所以 agent 不需要知道员工是谁,只需要带上 Ferry 签发的个人令牌:

1. 员工在 Ferry 网页上登录后,生成个人令牌。令牌只显示这一次。
2. 员工把令牌填进 agent 的 MCP 配置,作为请求头 `Authorization: Bearer <令牌>`。
3. Ferry 用令牌查出对应的人(如 `dingtalk:123`),所属部门从组织架构查询。

- Ferry 只保存令牌的哈希。令牌长期有效,直到员工作废它或重新生成。
- 组织架构同步发现员工离职时,自动作废其全部令牌,登录 cookie 也随之失效。
- 令牌只能调用发布相关的接口,不能代替网页登录访问应用。

**平台管理员**:由配置指定的用户 ID 名单。

**组织架构**

- Ferry 定时从平台拉取部门树、人员所属部门和在职状态,保存在自己的库里,服务启动时读进内存。
  权限判定只查内存里的这一份,不在每次访问时调用平台接口,也不查数据库。
- 每次拉取的是完整快照。应用前先检查:没有在职人员、没有根部门、上级部门不存在、上下级有环、ID 缺少平台前缀、
  在职人数一次减少超过 20% 且超过 10 人,任何一项不满足就整份拒绝,继续用原来的数据。
  这是为了防止数据源出问题(如接口权限不够只返回一部分)时,部门可见的应用一下子全都无法访问。
- **离职**:快照里没有了或标记为离职的人记为离职,**保留最后所属的部门**。这样离职者负责的应用不会一下子变成
  “只有自己可见”,同事照常访问,直到管理员停用或转交;离职的人自己不能再登录(任务 2.2)。
- 平台的变更推送需要平台能访问到 Ferry 的回调地址,先不依赖它,以定时拉取为准。

**“本部门可见”的规则**

访问者满足其一即可访问:

1. 和应用负责人至少有一个部门相同(一个人可以属于多个部门)。
2. 在负责人任一部门的上级部门里,逐级向上。

补充约定:

- **按负责人当前的部门判断**,不是创建应用时的部门。负责人调岗后立即按新部门生效。
- **根部门不算上级。** 根部门代表整个企业,直接挂在根部门下的人(通常是负责人或尚未分配部门的员工)
  如果算作上级,就能看到所有“本部门可见”的应用,等于全公司可见。
- 下级部门、平级部门不能访问。

### 与 AI Hub 的关系

AI Hub 是企业内部的另一个平台,负责统一身份、应用登记、数据接入和审计。它明确不接管应用的发布流程。

**决定:两个项目独立存在。** Ferry 不依赖 AI Hub 运行,不复用它的代码,也不替代它。
唯一的对接点是:通过 Ferry 部署的应用,其数据以后要能进入 AI Hub。这项对接现在不做,但设计上不能把路堵死。

AI Hub 的数据接入方式(依据其《独立应用接入指南》)是**平台来拉**,而不是应用往平台推:

- 应用提供一个导出接口 `GET /ai-hub/export`,AI Hub 带着平台服务身份的令牌按版本号增量拉取。
- 应用必须自己校验令牌和专用的访问范围 `ai_hub.ingest.export`。
- 应用要先在 AI Hub 登记对象类型和数据契约,经人工审核后才启用同步。

这对 Ferry 意味着三件事,都留到真正对接时再做:

1. **网关要给导出接口放行。** Ferry 让所有应用都处在登录之后,AI Hub 的拉取请求带的是服务令牌而不是员工登录态,
   会被登录网关拦住。对接时需要让 `/ai-hub/export` 这一个路径绕过登录,由应用自己校验令牌。
2. **应用需要 AI Hub 的配置。** 校验令牌要用到 AI Hub 的签发方地址等信息,由 Ferry 在发布时作为环境变量注入。
3. **模板要带导出接口。** 版本号单调、显式上报删除、数据脱敏这些硬要求不能指望 agent 每次都写对,应该在模板里实现好。
   AI Hub 的接入 SDK 是 Python 的,所以届时需要一个 Python 模板。

在 AI Hub 登记应用和数据契约需要人工审核,这一步保持手工,Ferry 不自动化。

## 6. 非功能要求

以下数字是初步假设,需要按企业实际规模确认:

- **规模**:第一年支持约 200 个应用、500 名发布者。
- **发布耗时**:90% 的发布在 5 分钟内完成。
- **可用性**:有了登录网关(任务 2.3)后,访问每个应用都要先经过 Ferry 的 `/authz`。Ferry 停了或出故障时,
  **所有应用都无法访问**(网关拒绝放行,这是安全上该有的做法)。发布、管理等功能同样依赖 Ferry。
  所以 Ferry 本身要稳定运行;是否要为它做多实例或高可用,等试用后按实际情况决定(会牵涉到单实例的假设,见 README)。
- **数据安全**:一期只在迁移前备份到服务器本机。全公司推广前做到:数据库每天备份,保留 14 天,存放在独立的 S3 兼容存储上(Dokploy 的备份只支持这种存储)。
- **安全**:管理面只在内网开放;平台凭据加密存储;所有操作可审计。

## 7. 成功指标

- **发布成功率**:首次发布无需人工介入即成功的比例,目标 80% 以上。
- **自动修复率**:失败的发布中,由 agent 自动修复成功的比例,目标 60% 以上。
- **发布耗时**:从确认到拿到地址的中位数,目标 3 分钟以内。
- **活跃度**:每月有人访问的应用占全部应用的比例。
- **人工介入量**:每 100 次发布需要平台管理员处理的次数。

## 8. 风险

| 风险 | 影响 | 应对 |
|---|---|---|
| agent 生成的应用不符合部署约定 | 发布成功率低 | 严格的模板和清单校验;给 agent 提供明确的约定说明 |
| Dokploy 接口随版本变化 | 升级后发布中断 | 固定 Dokploy 版本;适配器层隔离;升级前在测试环境回归 |
| Dokploy 许可证再次变更 | 可用功能受限 | 记录所用版本和许可证文本;只依赖 Apache 2.0 部分 |
| 没有审批,员工可以直接把应用开放给全公司 | 不合适的应用或数据在被发现前已经可以访问 | 默认仅自己可见;管理员可随时停用;审计日志可追溯。如果这个风险不可接受,可以加一条“应用对全公司开放时通知管理员”,成本很低 |
| 员工应用存在安全漏洞 | 数据泄露 | 所有应用都在企业登录之后;密钥扫描;应用间网络隔离 |
| Ferry 停机 | 所有应用都无法访问 | Ferry 稳定运行、出故障时告警(任务 3.5);以后视情况做多实例 |
| 恶意的员工应用冒充访问者 | 以访问者身份操作 Ferry 或别的应用 | Ferry 的登录 cookie 不发给应用;每个应用的网关 cookie 只对自己有效;健康检查口令按应用计算且到不了应用;伪造的身份请求头被网关删掉或拒绝 |
| 内网无法访问外网 | 构建失败 | 提前搭建依赖镜像源,并纳入第一阶段验证 |
| 钉钉、企业微信的接口权限受限 | 拿不到通讯录,无法按部门授权 | 读取通讯录需要企业管理员在开放平台授权,平台对自建应用的限制也可能调整;尽早用真实企业账号验证所需接口 |
| 工作通知被企业限制或员工没有及时看到 | 员工无法登录 | 登录页说明到钉钉或企业微信的哪里查看;验证码可以重新发送;以后需要时再加扫码登录 |
| 个人令牌泄露 | 别人可以冒充该员工发布应用 | 只存哈希;员工可随时作废重新生成;离职自动作废;令牌不能用于访问应用 |
| 应用数量增长超出服务器容量 | 平台不稳定 | 每人应用数配额和单应用资源上限;管理员停用不再使用的应用 |
| 数据库迁移破坏已有数据 | 员工数据丢失 | 迁移前备份到服务器本机;要求迁移脚本可重复执行 |
| 一期只有本机备份,服务器硬盘损坏 | 所有应用的数据全部丢失 | 试用前告知试用员工;全公司推广前完成异地备份(任务 3.4) |

## 9. 待确认的问题

这些问题的答案会影响任务规划,需要在第一阶段开始前确认:

1. 员工使用哪一种 agent 客户端?它是否支持接入远程 MCP 服务,能否在员工电脑上读取文件和执行命令?
   (已确认:有独立账号体系,不支持钉钉或企业微信登录,MCP 配置支持自定义请求头。)
2. 企业用钉钉还是企业微信?谁有权限在其开放平台创建企业内部应用,并授予读取通讯录和发送工作通知的权限?
3. 内网服务器能否访问外网?是否已有 npm、pip、镜像仓库的内部代理?
4. 是否已有内网 DNS 管理权限和内部证书签发机构?
5. 员工应用是否需要访问企业内部的业务系统或数据?如果需要,网络隔离的做法要重新设计。
